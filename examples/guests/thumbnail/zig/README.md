# `images.makeThumbnail` — a Zig plugin

This plugin implements the host-declared `images.makeThumbnail` interaction as
a zero-WASI Preview 2 component. The host supplies image dimensions; the plugin
calculates thumbnail dimensions. Boundary loads the artifact through
`@foxworth/boundary/plugin` or the native `boundary-plugin` crate.

Start with the [plugin guide](../../../../docs/guides/plugins.md) for the host
workflow. This reference explains the component's Zig implementation and ABI.

**This guest does arithmetic only. It does not decode or encode image
formats.** It takes a source width and height (as plain integers, handed to
it by the host through an import) and a requested max width, and returns a
scaled-down width and height. If you're looking for JPEG/PNG/WebP handling,
it isn't here — the host decodes the image before this guest ever runs, and
the host encodes whatever comes out. Read `src/thumbnail.zig` in full; it is
under 90 lines and contains the entire scope of what this component
"knows" about images: two multiplies, a divide, and a min.

## Why the ABI is hand-written

There is no maintained `wit-bindgen` generator for Zig. That's not a gap this
template papers over — it's the reason the template exists. Three paths were
available:

1. **Wait for or write a `wit-bindgen` Zig backend.** Bus factor one, and
   nothing to check in today.
2. **Target `wasm32-wasip1` and bring a WASI adapter.** Works, but drags in a
   WASI dependency for a guest whose actual footprint is "call one host
   function, do integer math." That's the opposite of the capability story
   this project is telling: an import list should be the whole truth about
   what a guest can reach.
3. **Target `wasm32-freestanding` and write the Canonical ABI glue by
   hand.** Zero WASI, runs on stable Zig, no dependency on a tool nobody
   maintains.

This template takes path 3. `src/main.zig` is the entire cost of that
decision — everything in it exists only because there is no generator to
produce it, and all of it was verified against
`wasm-tools component embed --dummy-names legacy`'s reference output (see
[Verification](#verification)) rather than against a spec reading alone.

## What's hand-written, and why each piece exists

The WIT world (`wit/guest.wit`, generated by `cargo run -q -p boundary-plugin
--example emit-wit` — do not hand-edit it) is:

```wit
interface footprints {
  images: func(request: string) -> result<string, string>;
}

world guest {
  import footprints;
  export images-make-thumbnail: func(input: string) -> result<string, string>;
}
```

Every function in this world takes and returns canonical JSON strings — the
JSON-string profile `wit.rs` documents, chosen because JSON Schema has no
total mapping onto WIT records and variants. That flattens to plain
`(ptr, len)` pairs at the core wasm level, which is what makes hand-writing
this tractable at all: there are no lists-of-records or nested variants to
lower, just strings in and strings out.

- **`cabi_realloc(ptr, old_size, align, new_size) -> ptr`** (`src/main.zig`)
  — the one allocation entry point Preview 2's Canonical ABI uses to move
  bytes across the guest/host boundary. It's called from two directions:
  the host calls it to get space in *our* memory before writing an argument
  string in, and the auto-generated canon-lower trampoline for our `images`
  import calls it to get space for a *returned* string. It's a thin wrapper
  over `std.heap.wasm_allocator` — alloc when `old_size` is 0, remap-or-copy
  when growing, free when `new_size` is 0.

- **The `images-make-thumbnail` export thunk** takes `(ptr: i32, len: i32)`
  and returns one `i32`. `result<string, string>` flattens to more core
  values (a discriminant plus a ptr and a len) than Preview 2's
  `MAX_FLAT_RESULTS = 1` allows through, so the return is indirect: this
  guest allocates a return area, writes the discriminant/ptr/len into it,
  and returns a pointer to it. That return area is a module-level `var`,
  not a stack local — `cabi_post_images-make-thumbnail` reads it in a
  *second* export call, after this one has already returned, so anything
  living on that call's stack frame would be gone by then.

- **`cabi_post_images-make-thumbnail`** — the host calls this once,
  immediately after reading the string this export returned. Its only job
  is to free the string bytes the export allocated; the return area itself
  is static, so there's nothing else to release.

- **The `images` import wrapper** lowers a Zig slice to `(ptr, len)` for the
  request, and — because its result is `result<string, string>` too —
  allocates a 12-byte return area *before* calling the import (for an
  import, the ABI's indirect-result convention runs the other way: the
  *caller* supplies the space, since the caller is the one who can free it
  afterward). That area can safely be a stack local: nothing reads it after
  this synchronous host call returns, unlike the export's return area above.

- **`entry = .disabled`, `rdynamic = true`** in `build.zig` — this is a
  reactor-style component with no `main`, and `rdynamic` is what keeps the
  Canonical ABI exports (which Zig otherwise has no reason to think anyone
  calls) from being stripped by the linker.

None of this reads or writes a pixel. `src/main.zig` is exactly the plumbing
above plus JSON parse/encode calls into `src/thumbnail.zig`, which is where
the actual interaction logic — and the only place this guest is "smart" — lives.

## The import is the authority story

`images-make-thumbnail` cannot compute a thumbnail size without knowing the
source image's dimensions, and it has no way to get them except by calling
the imported `footprints.images` function. That import is what makes Boundary's
capability story real rather than aspirational: this guest's WIT world lists
exactly one thing it can ask for, a host binds that name to a real
implementation (or refuses to bind it), and there is no other door in. This
template picks concrete request/response envelopes for that call — they are
this example's choice, not part of the WIT contract, which only guarantees
`string` in and `result<string, string>` out:

- Request: `{"imageId": "<id>"}`
- Success reply: `{"width": <int>, "height": <int>}`
- Error reply: `{"error": "<message>"}`

The guest's own export input, output, and error shapes (see
`src/thumbnail.zig`):

- Input: `{"imageId": "<id>", "maxWidth": <int>}`
- Success output: `{"imageId": "<id>", "width": <int>, "height": <int>}`
- Error output: `{"error": "<message>"}`

An unknown `imageId` is the declared domain error this template exercises
end to end: the host's `images` import returns `err`, and
`images-make-thumbnail` propagates it as its own `err`, prefixed with
context (`"source image lookup failed: <host message>"`). Out-of-memory is
the one condition this guest treats as an infrastructure fault instead — it
panics (traps) rather than returning `err`, because at that point nothing
about the guest's own certainty holds anymore.

## Build pipeline

```
src/main.zig, src/thumbnail.zig
        │  zig build-exe (wasm32-freestanding, entry=.disabled, rdynamic)
        ▼
   core module (.wasm)
        │  wasm-tools component embed wit/ --world guest
        ▼
   embedded.wasm (core module + component-type custom section)
        │  wasm-tools component new
        ▼
   thumbnail.component.wasm
```

`build.zig` runs both `wasm-tools` steps itself, so `zig build` alone
produces `zig-out/thumbnail.component.wasm`. There is no `--adapt` flag
anywhere in the pipeline: no WASI adapter is involved because no WASI import
exists to satisfy.

```console
$ zig build
$ zig build test      # pure src/thumbnail.zig logic, native target, no wasm runtime needed
```

`optimize` defaults to `release_small` (override with `-Doptimize=Debug` while
iterating on the ABI glue itself) — `Debug` mode's ubsan checks and debug
info alone take this from ~60KB to ~950KB.

(The `actual`/`shim` imports are `wasm-tools component new`'s internal

authoritative view of what a host actually sees, and it lists one import.)

**5. Byte size:** 61,830 bytes (`release_small`; ~963KB in `Debug`, mostly
ubsan runtime tables and `.debug_str`).

The compiled core module's export/import surface was diffed against
`wasm-tools component embed wit/ --world guest --dummy-names legacy -t`
(the reference template `wasm-tools` itself generates for this exact world)
and matches exactly: import `boundary:guest/footprints@1.0.0` / `images`, exports
`memory`, `cabi_realloc`, `images-make-thumbnail`, and
`cabi_post_images-make-thumbnail`, with identical core function signatures.
`--dummy-names legacy` is deliberate on the wasm-tools side too: the newer
`standard32` name-mangling scheme (`cm32p2|...`) is also accepted by
`component new`, but `legacy` is the scheme this template's exported symbol
names (`cabi_realloc`, `cabi_post_<name>`) are written against.

## What breaks when Component Model 1.0 lands

The Component Model's post-Preview-2 direction moves toward lazy,
multivalue-capable lowering — no more universal `MAX_FLAT_RESULTS = 1`
squeeze into a single indirect pointer. Zig cannot follow that change as-is:
Zig's C ABI has no multivalue return
([ziglang/zig#16639](https://github.com/ziglang/zig/issues/16639)), so a
future ABI that expects a guest export to return multiple flat core values
directly is not expressible from Zig's `export fn` today.

That's the whole reason this template pins itself to the *current*
ABI and to the JSON-string profile: every export and import here already
returns at most one flat value (a pointer to an indirect result), which is
exactly the shape Zig's calling convention can produce regardless of how
many-valued the *logical* result is. If Component Model 1.0 lands and
Preview 2's indirect-everything convention goes away, this template's hand
rolled glue stops matching what `wasm-tools` emits and needs to be rewritten
against the new ABI — there's no forward-compatible fallback path here, only
this file needing to change. Confining every guest signature in this world
to `func(string) -> result<string, string>` is what keeps that rewrite
contained to `src/main.zig` and out of `src/thumbnail.zig` and every other
guest that follows this one.
